# 92 — Design Review: Decisions & Open Questions

**Status:** Reference · **Area:** —
**Read when:** you need the *why* behind a rule, a rule cites a `D-n`, or you hit a gap the spec doesn't cover.
**Depends on:** [SPEC](../SPEC.md)
**Source:** review of the original design doc (deleted after the split) (2026-09-25)

## 1. Purpose

The original design doc is a strong direction but not yet buildable: its examples contradict its own rules in places,
and several mechanisms it relies on (test inputs, literals, inputs to `run`, number semantics) are undefined. Each
problem found is resolved here as a **decision** `D-n` — binding unless the owner overrides it — or, where the choice
is the owner's to make, an **open question** `Q-n` with the default the spec uses until answered.

Changing a decision: edit its row (keep the id, add "revised YYYY-MM-DD"), then update the rules that cite it.

## 3. Decisions

| ID | Decision | Rationale |
|---|---|---|
| **D-1** | Name **Velme**. File extension `.velme`; CLI `velme`; crates `velme-*`; GitHub org `velme-lang`, repo `velme-lang/velme`; optional file header `language: velme/0.1`. | Owner's rename. |
| **D-2** | **Retired** — superseded by D-36 (was: `Number` is IEEE-754 binary64). | Owner chose exact decimal (Q-1). |
| **D-3** | All goal parameters and outputs carry explicit types in v0.1. The untyped beginner form is Future (inference or playground templates, Q-3). | Keeps sema and the IR contract simple (P-3, P-5). |
| **D-4** | `result` is reserved. In checks it names the goal's output. In a `call` block, a binding named `result` makes it the goal's output (type must match): the goal is **wired** — no synthesis, the plan is documentation. A goal must have a `plan`, a `result` binding, or both. | Makes Test 2 (§52) meaningful and gives learners a fully deterministic composite goal with zero LLM cost. |
| **D-5** | The call DAG is compiled from source by the compiler. For a composite goal, the LLM synthesizes only the **tail**: an IR expression over the inputs and call bindings (as `Local`s). Synthesized IR may not contain `Call` nodes; the IR validator rejects them. | Enforces INV-6 structurally: the LLM can't change what is called. Simplifies the prompt and the validator. |
| **D-6** | Check DSL additions: arithmetic `+ - * /`; `if A then B` (≡ `not A or B`); `some x in xs has P` beside `every`; list projection `xs.field` → `List<F>`; `and`/`or`/`if-then` short-circuit and **narrow** `T?` to `T` after `is not empty`/`is empty`. Field access on an un-narrowed `T?` is a type error (`VL0207`). Check scope: inputs, call bindings, `result`. | Fixes F-3, F-18, F-19 with the smallest additions a learner can read aloud. |
| **D-7** | New `examples:` block: each item is an equality between a call of the goal itself and an expected value, using literal syntax — `Player(name: "Lina", jump_height: 3, score: 820)`, `[1, 2]`, `nothing`, `true`, `"text"`, numbers. Examples run first in verification and in `velme test`. | Fills F-8; reuses the check expression grammar; literals are needed for `velme test` anyway. |
| **D-8** | `budget` is v0.1: optional line `budget cpu=10ms memory=4mb calls=16 depth=4`, keys optional, can only tighten system caps for **that goal's own invocation** — never raise, and never "including its calls" or a caller's remaining allowance (revised 2026-09-27, aligned with D-27's per-invocation model). `cpu=` takes only whole `ms`, no `s` unit (revised 2026-09-27); every budget value is a digit-only whole number, no `.` (D-78). `pure` is reserved (v0.1-ready); every v0.1 goal is pure. | F-5. Budgets exist in the runtime anyway; exposing them costs little. Per-invocation limits keep concurrent siblings independent (INV-3, INV-5; `runtime/30` R-RUN-17). |
| **D-9** | When any binding in a wave fails, every sibling in that wave still runs to completion — no cancellation — and no later wave starts; the reported failure is the failure of the **lowest source-order** binding among the wave(s) that ran, with every other failure in those waves listed as a note in source order (revised 2026-09-27, was: still-running siblings cancelled). Traces list calls in source order, not completion order; a binding in a wave that never started appears as `skipped`. | Deterministic error results and traces (INV-3). Running siblings to completion removes a race between "cancel" and "finish" that made trace outcomes depend on scheduling even though the reported failure was already deterministic (`runtime/30` R-RUN-09). |
| **D-10** | Fuel (deterministic) is the primary CPU limit and yields `BudgetExceeded`. Epoch/wall-clock is a safety net and yields `Timeout`, which is marked non-reproducible in the trace and never cached as a verification outcome. Reproducibility tests use fuel. | F-14. |
| **D-11** | Synthesis cache key = hash(normalized goal source, **child signature** fingerprints, language/compiler/IR/builtins/prompt versions, provider+model id). Execution identity (the artifact graph) pins concrete child artifacts separately. | Regenerating a leaf doesn't re-synthesize its ancestors; saves LLM cost and keeps locks stable. |
| **D-12** | `velme.lock` (TOML, committed) maps each goal to its accepted IR artifact hash; artifacts live in `.velme/artifacts/` (content-addressed, committable). `--locked` never synthesizes and fails if the lock is stale; CI uses `--locked`. WASM modules are a derived local cache, not locked (deterministic from IR + compiler version). | F-12; offline use (INV-7); reviewable diffs of generated code. |
| **D-13** | `SynthProvider` trait with providers `anthropic` (MVP real), `replay` (reads recorded exchanges from fixture files), `scripted` (unit tests). Live-LLM tests are opt-in (`VELME_LIVE_LLM=1`) and never part of the default gate. | Deterministic, free, fast CI; the repo's own test suite never depends on a vendor. |
| **D-14** | MVP ships one real provider: Anthropic Messages API with JSON-schema-constrained output; model id is configuration (`velme.toml` / `VELME_MODEL`), never a code constant. Second provider after MVP. **Amended by D-41:** Ollama also ships in the MVP. | §37 "one LLM provider"; vendor-neutral trait keeps INV-7. Owner may pick another (Q-2). |
| **D-15** | Right-sized workspace: `velme-syntax`, `velme-diagnostics`, `velme-sema`, `velme-ir`, `velme-check`, `velme-builtins`, `velme-interp`, `velme-synth`, `velme-runtime`, `velme-wasm`, `velme-cli`, `velme-test-support`. No top-level `compiler/`, `runtime/`, `stdlib/` trees in v0.1. Split a crate only for a real API/ownership boundary. | F-16. |
| **D-16** | Roadmap order: M0 repo → M1 syntax → M2 semantics → M3 IR + interpreter + checks + fingerprints, store and lockfile (hand-written IR installed by a test helper) → M4 DAG runtime + budgets + trace → M5 Spellbook → M6 CLI completion (`--locked`/`--offline`, `artifact`, config) → M7 WASM + Wasmtime → M8 MVP gate. Playground and Coach are post-MVP. Revised 2026-09-27: store and lock moved from M6 to M3. | F-15; each phase is testable without the next — `replay` lookups, M5's lock/store criteria and M3/M4's `velme run` all need the store and lock (architecture review 2026-09-27). Details: `delivery/50`. |
| **D-17** | Error codes are `VL` + 4 digits: `VL01xx` syntax · `VL02xx` names/types · `VL03xx` calls/graph · `VL04xx` IR/synthesis · `VL05xx` checks/examples · `VL06xx` runtime/budgets · `VL07xx` artifacts/lock · `VL08xx` capabilities · `VL09xx` CLI/IO. Original `A001…A014` map in `reference/90`. Prefix revised 2026-09-27 with D-1. | F-23; INV-10. |
| **D-18** | A v0.1 program is one file. `type` and `goal` declarations are order-independent within the file; bindings inside a `call` block must be defined before use (§12.5). | Modules are Future (RFC). |
| **D-19** | Indentation: spaces only (a tab in leading whitespace is `VL0103`); any consistent width, 4 recommended. `plan: \|` starts a block scalar that ends at the first line indented at or below the `plan` key. | Python/YAML-like layout children already meet; deterministic lexing. |
| **D-20** | Checks run on every `velme run` in v0.1, not only during verification. A failure is `VL0501 CheckFailed` with the assertion and the values involved. | Teaching value; they are also the goal's runtime contract. |
| **D-21** | Hashing: BLAKE3 over canonical JSON — keys sorted by Unicode code point (= UTF-8 byte order), strings escape only `"` `\` and U+0000–U+001F (short forms `\b \f \n \r \t` where they apply, else lowercase `\u00xx`, everything else raw UTF-8 with no normalization), numbers in plain decimal per R-TYP-08, no insignificant whitespace, duplicate object keys rejected on input (`VL0401` for IR, `VL0902` for input JSON) (`compiler/21` R-IR-21, revised 2026-09-27). Plan text normalization: LF newlines, trailing spaces and tabs (U+0020, U+0009 only) trimmed per line, the content column removed (D-73) — internal spacing and all other whitespace preserved (revised 2026-09-28). | Stable fingerprints across platforms; spelling out RFC 8785 (JCS) closes the ambiguity a hand-rolled "canonical JSON" leaves in key ordering and escaping (INV-3, INV-8). |
| **D-22** | No implicit randomness. Builtin `random(seed, index) -> Number` in `[0, 1)`, SplitMix64 over (seed, index), mapped to 18 decimal places (R-BLT-04, revised 2026-09-27); `seed`/`index` must be integer-valued (else `VL0602`). `range(n) -> List<Number>` provides indices. Runtime seed derivation (§32) is Future, with `effects: random`. | F-10; reproducible procedural generation with explicit data flow. |
| **D-23** | Inputs: `velme run FILE --goal G --input FILE.json` (or `-` for stdin), or repeated `--arg name=<json>`. JSON mapping: Number↔number, Text↔string, Boolean↔bool, Nothing↔null, `List`↔array, record↔object with exactly the declared fields (unknown/missing → `VL0902`). Output: same mapping. | F-20; one mapping shared by CLI, examples, fixtures and IR literals. |
| **D-24** | Reserved words for Future features: `pure effects when choose otherwise import module fallback retry optional assume` (`assume` added by D-39). Using one is `VL0104 ReservedWord` ("coming in a later Velme version"). | Keeps later additions non-breaking. |
| **D-25** | Tree-sitter grammar is post-MVP; when added, it must parse the whole `tests/golden/parser` corpus with the same accept/reject outcome as the Chumsky parser. | Prevents two-grammar drift. |
| **D-26** | Two keys refine D-11: `contract_key` (goal source, child signatures, language version, IR major, builtins version) decides lock staleness and seeds generated test inputs; `synthesis_key` = `contract_key` + prompt version + compiler MAJOR.MINOR + provider + model is the store/replay-fixture key. | Switching model/prompt or a compiler patch release never forces a locked project to re-synthesize (`runtime/32` R-ART-03/04). |
| **D-27** | Budgets are per invocation, not a shared pool; `max_goal_calls`/`max_call_depth` are checked statically by `velme check` (the call graph is static). Velme fuel is a fixed per-IR-node cost table and memory a fixed value-size function, metered identically on both backends; Wasmtime's own limits are backstops. `budget cpu=Nms` converts to fuel by a fixed constant. | Budget failures are deterministic and backend-independent (INV-3, INV-5); `runtime/30` R-RUN-04/16/17. |
| **D-28** | `velme run`/`test`/`trace` never synthesize unless `--build` is passed; a stale/missing entry is `VL0702`/`VL0701` with a hint. Only `velme build` (or `--build`) writes the lock. | No surprise LLM cost; `runtime/32` R-ART-16, `tooling/40` R-CLI-03. |
| **D-29** | IR has an expression-level `if` (`Condition`) in v0.1; conditional *calls* remain Future. | Leaf goals like `FindBadge` (§44) need it; `compiler/21` R-IR-06. |
| **D-30** | WASM: only leaf goals compile to WASM in v0.1 (composite tails stay on the interpreter); values cross in a fixed type-directed linear-memory layout (no JSON inside WASM); builtins are host imports backed by the same `velme-builtins` code. v0.1 has no effectful host functions. | Smallest ABI; one builtin implementation for both backends; `runtime/31`. |
| **D-31** | `call` arguments are paths or literals only — no arithmetic or builtin calls (`VL0303`). | Keeps the call block pure wiring; computation belongs in plans; `language/12` R-GOAL-08. |
| **D-32** | A runtime error while evaluating a check item fails that item with `VL0501` (cause attached); exhausting the budget during checks reports the budget failure. | `language/13` R-CHK-07/08. |
| **D-33** | Record types are nominal; record values compare structurally; a record literal names every field, nullable ones included. `is empty` on a non-nullable record is `VL0206` with a hint. | `language/11`. |
| **D-34** | `maximum`/`minimum` return `Number?` and narrowing does not flow through builtin calls — "biggest" checks are written with `every`. Extra v0.1 builtins: `sum abs floor ceil round clamp concat to_text range`; IR-only `map filter find reduce sort_by all any`. | `language/14`. |
| **D-35** | Identifiers are ASCII in v0.1; numbers have no exponent form; naming conventions are uncoded lint warnings. | `language/10`. |
| **D-36** | `Number` is an exact decimal (coefficient `< 2^96`, scale ≤ 28, half-to-even rounding; `language/11` §3). Division by zero and overflow are `VL0602`. **Not configurable**: a project or flag switch would give the same source two meanings — fingerprints, locks, examples and checks would depend on config, the LLM contract would be ambiguous, and every backend would need both. A separate opt-in binary `Float` type is Future. The implementation may wrap `rust_decimal` only if property tests show it matches R-TYP-04 exactly. WASM uses host imports for arithmetic (`runtime/31` R-SBX-06). | Answers Q-1. Kids-first and money examples need `0.1 + 0.2 == 0.3`; changing `Number` after launch would silently change existing results. One shared Rust implementation makes interpreter/WASM parity (INV-3) simpler. |
| **D-37** | Learner privacy for v0.1: CLI only, user's own key, no telemetry leaves the machine, plus a one-line notice on each build that calls a live provider (`tooling/41` R-SEC-12). Any hosted, classroom or child-directed product needs legal review and an approved consent/retention policy (COPPA, GDPR-K) first. | Answers Q-4. |
| **D-38** | Code is `MIT OR Apache-2.0`; spec and docs CC BY 4.0; the name and logo are trademarks, not licensed. Name screened 2026-09-27 (`delivery/52` §11): `velme` free on crates.io, PyPI and npm; org `velme-lang` and domains `velme.dev`, `velme.org` free; USPTO and TMview searched 2026-09-27: no live VELME mark in classes 9 or 42 (Ukraine m202402581, classes 9/42, ended); WIPO 1860545 "Velme" is live outside software; near marks Velmeo (DE 3020262350429, class 9, consumer goods) and VELMERE (US 98399957, eyewear) are low risk. An attorney's clearance opinion is owed before filing a mark; a class 42 filing avoids Velmeo. Diagnostic prefix follows the name (`VL`, D-17). | Answers Q-5. Dual licence is the Rust ecosystem norm. |
| **D-39** | No `assume:` block in v0.1; a check failing on a generated input shows the counterexample and suggests the `if … then …` rewrite (`compiler/22` R-SYNTH-19). `assume` is reserved (D-24) so adding it later breaks no program. | Answers Q-7. The check language already expresses preconditions (D-6). |
| **D-40** | **Retired** — superseded by D-65 (was: contributor instructions split across `CONTRIBUTING.md`, `AGENTS.md` and `CLAUDE.md`). | Owner moved agent instructions out of the public repo (2026-09-28). |
| **D-41** | The MVP ships a second real provider, `ollama` (local models), next to `anthropic`: Ollama chat API, IR JSON Schema as `format`, temperature 0, no key. `model()` is `<model>@<digest>` resolved from the server once per build. `--offline` stays strict and constructs no provider, local ones included. Amends D-14; moves "local models" from Future to v0.1. | Owner request 2026-09-26: synthesis without an account or sending plans off the machine. The provider trait already made it cheap (INV-7); validation and checks keep weaker models safe (INV-1, INV-2). |
| **D-42** | Human-written implementations come through an `external` provider, not through Velme source: Velme sends each synthesis request as JSON to a user-chosen command and validates and verifies the IR it returns like any LLM reply. The command comes only from a flag, env var or user-level config; it gets no API keys; `max_retries` defaults to 0. No `impl:` block or other source syntax is added. | Owner request 2026-09-26: keep the language free of implementation code (P-1) while letting people or tools replace the LLM per project. One protocol also lets any other LLM stack plug in without core changes. |
| **D-43** | A failed synthesis says why, and the AI helper may ask instead of guessing. `VL0403` names the cause shared by most attempts, using only Velme-produced text. A reply may be `{"question": "<text>"}`: it stops that goal with `VL0407` and no retry, and the build never waits for input; the answer goes into the goal, preferably as an example (verified) rather than plan text. Amends D-42: the `external` backend may reply with a question too. | Owner request 2026-09-26: learners shouldn't need `--verbose` to know what to fix, and R-SYNTH-10 turned a question about an ambiguous plan into a guess that could pass the checks unseen. Keeping the answer in source keeps builds non-interactive and reproducible (INV-3) and the choice reviewable. |
| **D-44** | Synthesis token cost is cut by options, not by weaker checks (`compiler/22` §4.1, `tooling/40` §5.1). The prompt puts the parts shared by every goal first so `anthropic` can cache them (`prompt_cache`, default on); the reply schema goes through the provider's constraint with only a one-line-per-node summary in the prompt (`schema_in_prompt`, default `summary`); retries carry only the latest failed reply (`retry_history`, default `latest`) and stop when two attempts in a row share a cause (`stop_on_repeat`, default on); at most `max_prompt_examples` (8) examples are sent. User-selectable: `reply_format = "compact"` (short aliases, expanded to canonical IR before validation) and `retry_model` (a different model for retries). Options that change what is sent enter `synthesis_key` through `input_version`, never `contract_key`. | Estimated per goal: 4.5–9k input and 0.1–3k output tokens per attempt, 25–45k input in the worst case of 4 attempts with full history. The fixed prefix is about 4–6.5k of each attempt's input. Defaults take the savings with no trade-off in what is accepted; `compact` (about 30–50% fewer output tokens, but a format the model has never seen) and `retry_model` (price against success rate) are trade-offs the owner wanted users to choose. Measure with the M5 replay fixtures and the build summary (R-SYNTH-21). |
| **D-45** | An `external` backend may reply `{"pending": "<text>"}` when the request is queued for a person or tool and has no answer yet (`compiler/22` R-SYNTH-41). The goal stops with `VL0408 SynthesisPending` and no retry; nothing is stored or cached, so the next build asks again. The build still never waits (D-43). Amends D-42. | Owner request 2026-09-27: one person writes goals and builds, another receives the requests and implements them. Reporting "not answered yet" as `VL0406 BackendFailed` told the writer something broke. A separate code keeps the two apart for learners and for tools reading `--json`; builds stay non-interactive (INV-3), and the answer still passes validation and verification (INV-1). |
| **D-46** | A locked/stored artifact's manifest claims (`goal`, `signature`, `contract_key`) are informational; trust comes from re-verification, not from the manifest matching. Every load cross-checks those fields against the lock entry and against the key computed from current source (`runtime/32` R-ART-10); a mismatch makes the entry stale (`VL0702`, R-ART-14). When `build` accepts a goal's artifact from the store instead of freshly synthesizing it, and for `velme test --locked`, Velme re-runs that goal's `examples:` and the generated-input check suite (`compiler/22` §6) — deterministic, offline, no provider call — before trusting it. `velme run` does not re-verify: hash check, IR validation and the manifest cross-check only. CI is expected to run `velme test --locked`, not just `velme run --locked`. | Owner decision 2026-09-27, architecture review: a tampered but internally-consistent artifact/lock pair (matching hash, matching manifest, edited behavior) would otherwise run unexamined (INV-1). Re-verification is only as strong as the goal's own examples/checks/generated inputs — the same limit synthesis already accepts for LLM output — but it costs nothing extra since the suite already exists. `run` stays cheap and offline-fast (INV-7); tests are where the safety property lives. |
| **D-47** | In human-mode output, every string Velme did not itself produce — external backend stderr and `{"error"}` reasons (`VL0406`), `{"question"}`/`{"pending"}` texts, values computed by synthesized IR shown in `Got:` lines, trace text, and input echoes — is escaped before display (`tooling/40` §3.5): C0/C1 control characters (except the newline and tab a layout expects), ESC/ANSI/OSC sequences, and Unicode bidi controls (U+061C, U+200E, U+200F, U+202A–U+202E, U+2066–U+2069) render as visible escapes such as `\u{1b}`. `--json` writes the same characters as `\uXXXX`, since JSON's own escaping covers only C0 (revised 2026-09-28). R-SYNTH-33's control-character cleaning for question/pending text is a separate, additional length/format rule for that one field; this decision is the general display-time rule. | Owner decision 2026-09-27, architecture review: an external command, a synthesized value, or a trace can carry attacker-controlled bytes (T-13) that a raw terminal would interpret as cursor moves, clipboard writes (`OSC 52`) or right-to-left overrides — a terminal-escape-injection risk unrelated to IR safety. Escaping at the rendering boundary keeps INV-1/INV-4 (the LLM's only power is IR, not the terminal) meaningful all the way to the user's screen. |
| **D-48** | Compiled WASM modules are cached in a user-level cache directory (`$XDG_CACHE_HOME/velme/wasm/`, or the platform equivalent), never inside the project (`runtime/31` R-SBX-13/14, revises D-12's "derived local cache" to name the location). The cache key stays artifact hash + BLAKE3(`velme-wasm` version, Wasmtime version, engine config); `Module::deserialize` only reads from that user-level directory, never from anything under the project (e.g. `.velme/`). A `velme cache clean` command (`tooling/40`) deletes it. | Owner decision 2026-09-27, architecture review: a `.cwasm` file is native, pre-validated code; if Wasmtime would deserialize one found inside a cloned project, a repository could ship a payload that skips IR validation and the sandbox's own compilation step entirely (T-11, INV-1). Moving the cache off the project closes that path structurally, matching "anything from the project is untrusted" (`tooling/41` T-10). CI must not restore this cache across a trust boundary (e.g. from a fork's PR), since a fork could otherwise plant a stale-but-matching-key module for a shared runner user. *(revised 2026-09-27 for D-12: the WASM cache's location is now defined here, not left implicit.)* |
| **D-49** | `--json` output is a versioned envelope, `"format": "velme-cli/1"`: `status` (worst outcome), `results[]` (per goal: `goal`, `status` ∈ `ok \| failed \| pending \| blocked \| skipped`, `diagnostics[]` as R-CLI-08), `notices[]` (R-SEC-12), and for `build` a `summary` (R-SYNTH-21). `pending` reports `VL0408`; `blocked` reports `VL0409 SynthesisBlocked` (D-56). | **D-51** | The whole run's deterministic bound is static: at most `max_goal_calls` × `max_fuel` (1.28 × 10⁹ fuel, about 12.8 s at `FUEL_PER_MS`), already enforced by `velme check`'s call-count limit (`runtime/30` R-RUN-17, R-RUN-24); there is no separate fuel envelope. `max_wall_clock` rises from 2 s to 60 s, well above that bound, and is a safety net against a Velme bug or an overloaded host only; its clock is injectable so tests drive it deterministically (R-QA-02). `VL0603` is an environment failure: verification (`compiler/22` R-SYNTH-14) never rejects a candidate because of it — it reports an infrastructure error, and the attempt is not consumed. | **D-52** | Fuel costs for the `language/14` builtin catalog are size-proportional, not flat, and depend only on input sizes: scalar ops cost 1; list builtins cost 1 + items touched (`contains` up to and including the match, `sum`/`range(n)` 1 + n, `length` 1); text builtins cost 1 + ⌈bytes/64⌉ of the input(s) (and of the output where it is larger; for `concat` the two inputs' bytes are summed before rounding, so it costs 1 + ⌈output bytes/64⌉, clarified 2026-09-29); `to_text` costs 1 + ⌈output bytes/64⌉; `==`/`!=` on composite values cost 1 + the scalar leaves compared, stopping at the first difference; `sort_by` costs 1 + n·⌈log2(n+1)⌉ plus 1 per key evaluation (a fixed formula, never counted comparisons); `random` costs 1. | **D-53** | Memory accounting (`runtime/30` §7.1) is a monotonic count of bytes **allocated** during an invocation, not the peak of live bytes; it uses the value-size table (Number 16, Boolean 8, Nothing 0, `T?` 8 + `T`, Text 16 + bytes, List 16 + Σ items, Record 16 + Σ fields), never less than a value's bytes in the WASM ABI's 8-byte slots (`runtime/31` §3). | **D-54** | `velme-runtime`, not `velme-synth`, decides lock/store staleness and performs the lookup order of `compiler/22` R-SYNTH-02, calling into `velme-synth` only for goals that need synthesis. | **D-55** | When `velme build` changes a child's artifact, it re-runs every ancestor composite's examples and checks against the new children with no LLM call (`runtime/32` near R-ART-02). | **D-56** | When a goal ends synthesis with no artifact (`VL0403`, `VL0407`, `VL0408`, or `VL0409` itself), none of its ancestors is synthesized; each ancestor instead ends with `VL0409 SynthesisBlocked` ("`{goal}` wasn't built because `{child}` {reason}."), with the child's code as a note. `VL04xx` still exits 2. | **D-57** | "Fully cached" means every goal in the build is fresh in the lock, in which case the build makes no provider contact at all — no Ollama request, no external command start (`compiler/22` R-SYNTH-24..26). | **D-58** | `all(list, T -> Boolean) -> Boolean` and `any(list, T -> Boolean) -> Boolean` are dedicated IR node kinds (`compiler/21` §3), not `builtin` calls: a list operand and a one-parameter lambda, elements visited in list order (R-BLT-07). `all` short-circuits at the first `false` and is `true` for `[]`; `any` short-circuits at the first `true` and is `false` for `[]`. | **D-59** | The IR sort node is `sort_by` (not `sort`): `(list, T -> Number, descending: Boolean) -> List<T>` (`compiler/21` R-IR-07). | **D-60** | On an optional collection — `List<T>?` or `Text?` — `is empty` is `true` for `nothing` **and** for a present but empty value (`[]` / `""`); `is not empty` is its negation and narrows to the non-optional `List<T>` / `Text` (`language/11` R-TYP-25, R-TYP-22). The `is_empty` IR node (`compiler/21`) implements the same rule. | Architecture review 2026-09-27: a learner writing `if xs is empty then …` on a `List<Number>?` means "nothing to do here", which is true whether the list is absent or present-but-empty; forcing two checks (`xs is empty or xs.length == 0`, itself blocked by R-TYP-12 until narrowed) would fight the language's own progressive-disclosure goal (P-2). |
| **D-61** | `eq`/`ne` operands may differ in type when one is assignable to the other (`language/11` R-TYP-20 — already states this), not only when both sides are the same type: a `Number` may be compared with a `Number?`. | **D-62** | A `call` block binding may be named `result` (D-4) — the grammar changes from `binding = NAME "=" …` to `binding = (NAME \| "result") "=" …` (`language/10`), since `result` is otherwise a keyword and could never lex as a `NAME`. `result` may only be the **last** binding; naming any earlier binding `result`, or using `result` as a call argument, is `VL0101` ("`result` can only name the last binding") — a plain syntax error, not `VL0104` (which stays reserved for the D-24 words, `language/10` R-SYN-05, `language/12` R-GOAL-23). | Architecture review 2026-09-27: the wired-goal example (`language/12` §8.3, D-4) already writes `result = AddOne(doubled)`, which the grammar as drafted could not parse; restricting `result` to the last binding keeps "wired vs. synthesized" a single, front-loaded decision instead of something a mid-block rename could silently flip. |
| **D-63** | An unknown built-in name fails IR validation stage 3 (Names) with `VL0402`, exactly like any other unresolved name — not stage 5 (Capabilities) with `VL0801` (`compiler/21` §6). `VL0801` keeps its original meaning: a module requesting a host function or capability it wasn't granted (INV-4); v0.1 goals request none, so it is currently only reachable by a future module. | **D-64** | A `type` or `goal` declared with a built-in's name is allowed but is a lint warning suggesting a rename (the naming-convention mechanism of `language/10` R-SYN-06 — no new diagnostic code), because it cannot actually collide: goals are never called from checks (`language/13` R-CHK-03) and built-ins are never called from a `call` block (`language/14` R-BLT-02). Design after M4, reusing the WASM emitter's parity tests. | Open · default: Future, not v0.1 |
| **Q-16** | Share goals as packages without re-synthesis on import? If yes: a package ships source, `velme.lock` and its artifacts (runtime/32 §3); import pins artifact hashes in the importer's lock, rejects a hash mismatch or a stale `contract_key` (never falls back to synthesis), re-validates every IR goal (INV-1, INV-4, INV-6) and may re-run its checks deterministically (INV-2); no provider is needed. Parents key on child signatures (D-11), so a signature change is a major version, a stricter contract minor, a new artifact for the same contract patch. Open points: `export` visibility, qualified names, git/path dependencies first then a registry (Q-13), imported budgets counted against the caller (INV-5). Needs an RFC (D-18, D-24). | Open · default: Future, not v0.1 |
| **Q-17** | Checks on a record type (`type Amount` … `check: value >= 0`) instead of classes? Classes are rejected: mutable state breaks goal purity and deterministic checks (INV-2), and dynamic dispatch breaks the static call graph (INV-5, INV-6); grouping belongs to modules (Q-16), polymorphism to enums and generics (R-TYP-02), state to effects (Q-14). A type check runs, in the same engine as goal checks, on every value of that type a goal receives or returns. The same mechanism gives checked aliases of built-in types in place of new primitives: `type Count = Number` with `check: value == floor(value)` instead of an `Int` type, which is rejected because a second numeric type undoes D-36's single `Number`, needs mixed-arithmetic promotion rules (R-TYP-04..06), and splits the collection built-ins under invariant lists (R-TYP-13). Open points: whether type checks enter the type's `signature` (runtime/32 §2), so tightening one re-keys parents; test-input generation (R-SYNTH-17) producing only values that pass; a new diagnostic code (INV-10); for aliases, whether `Count` and `Number` are mutually assignable (checked on narrowing) and whether `+ - *` on two `Count`s yields `Count` (`/` always yields `Number`). Needs an RFC. | Open · default: Future, not v0.1 |
| **Q-18** | Time types, designed together: `Date` (calendar date), `DateTime` (civil date and time, no zone), `Instant` (absolute UTC point) and `Duration`. Values only ever come from input, literals or examples; reading the clock is an effect (Q-14), never a built-in, so checks stay deterministic (INV-2). One exact integer representation per type (no binary float, D-36) keeps interpreter and WASM identical (INV-3); JSON maps to RFC 3339 text. Open points: zones (converting `Instant` to civil time needs a tz database whose version changes results, so it would have to be pinned in the lock and in `signature`, runtime/32 §2, or zones stay out); leap seconds (ignored, as in Unix time); month and year arithmetic on short months (clamp or fail); precision of `Instant`/`Duration`; whether `Duration` replaces the budget units (`language/10` UNIT). Needs an RFC. | Open · default: Future, not v0.1 |
| **Q-19** | Self-hosting: write the Velme compiler in Velme? Proposed answer: a non-goal for the trusted core. The validator (INV-1), runtime, sandbox and budgets (INV-4, INV-5) stay deterministic, human-reviewed Rust, because synthesized IR that has only passed bounded checks (INV-2, R-SYNTH-18) cannot be the thing that checks synthesized IR. Tooling outside the trust boundary (linters, reporters, test-data helpers) may be written in Velme once the language can express it: recursion, loops and ADTs are all Future (R-GOAL-11, R-GOAL-17, R-TYP-02). The conformance suite may use Velme check blocks run against the Rust compiler. The Playground (Future) follows the same line: its compiler, validator, runtime, sandbox and synthesis stay Rust compiled to WASM, while its screen flow and lessons (ordering, unlocking, hints, exercises with their examples) may be Velme goals run on that core, using the UI model of Q-21; the first Playground is written without them and migrates once that model, effects (Q-14) and modules (Q-16) exist. | Open · default: non-goal for the trusted core |
| **Q-20** | Prove checks instead of only testing them? Checks run on at most 64 generated inputs (R-SYNTH-17, R-SYNTH-18), so a stronger model can pass them and still be wrong between those inputs. Verified IR is loop-free, total and call-bounded (R-IR-06, INV-6), which makes it a candidate for deciding a check for all inputs with an SMT solver, falling back to the bounded set when undecided. Open points: exact-decimal (D-36) and `Text` theories; solver version and timeouts, which must be pinned so results stay deterministic (INV-2, INV-3); whether a proof is recorded in the lock (runtime/32); how it interacts with preconditions (Q-10) and counterexample shrinking (Q-8). This is the main post-v0.1 research direction. Needs an RFC. | Open · default: Future; bounded checks only (v0.1) |
| **Q-21** | Which domains beyond programming should Velme target once Future features land? The fit is any task a person can state as typed inputs, outputs and deterministic checks, whatever their coding skill: workflow and business-process automation (conditional calls, `retry`/`fallback`, effects; the structure stays author-fixed, INV-6), capability-bounded integrations and agents (R-SEC-04, Q-14), rules engines and regulated calculations (D-36, Q-18, Q-20, Q-15), data pipelines (`storage`/`network` effects, maps), sandboxed plugins (runtime/31, INV-5) and teaching outside computing (Playground, D-3). Out of scope whatever lands: tasks whose correctness is a judgement (INV-2; a `network` effect calling an LLM service could verify only the output's shape), visually driven interfaces, and low-level or hard-real-time code. Proposed answer for UI: logic-driven interfaces (apps, forms, dashboards, quizzes, simple 2D games) as two pure goals, `View(state) -> Screen` returning a typed UI tree and `Update(state, event) -> state`, with a host renderer outside the trust boundary doing all drawing and input (INV-4); checks cover structure and accessibility, never looks (INV-2), so styling is author-declared, not synthesized; events dispatch through `choose` over an event enum (D-24, INV-6); recorded events replay a session exactly (INV-3). Needs enums, `choose`, nested types and the effect design (Q-14); not for visually driven or per-frame-heavy UI. Open points: whether to pick a lead domain that orders Future work; the `Screen` vocabulary and first host (browser via WASM or terminal); how an LLM called at run time through an effect is traced and replayed (INV-3). | Open · default: no lead domain; Future order follows `delivery/50` |
| **Q-22** | Offer `velme build --batch` for non-interactive builds (CI, large rebuilds) through a provider's batch API, at about half price but with results that can take minutes to hours? Needs a batch-aware provider call and a build that can wait or resume. A shared store (Q-13) is the other large saving, since a hit costs nothing. | Open · default: no; builds call the provider directly (D-44) |
| **Q-23** | Ship a small standard library of goals, so common steps never ask an LLM? Proposed answer: yes, after Q-16. Each goal is ordinary Velme source (plan, checks, examples) whose IR is hand-written and reviewed by maintainers, never synthesized; it ships as a locked package (Q-16) versioned with the compiler, is validated like any IR on load (INV-1, INV-4, INV-6), runs its checks and examples in the gate (INV-2), and is in the interpreter/WASM differential tests (INV-3). Programs use it from `call` blocks, so a parent sees only its signature (D-5, D-11) and a build makes zero provider calls for it. Scope is compositions learners write often that no single builtin covers (e.g. `Average`, `Median`, `Percent`), not duplicates of builtins (D-34). Open points: v0.1 has no generics, so goals take concrete types only; the name set is reserved for good once published; how a program imports it (Q-16, D-18). Rejected alternative: an inline `result:` expression body per goal (owner, 2026-09-27), since hand-written computation in source works against plans as the place computation is described (D-31). | Open · default: Future, after Q-16 |
| **Q-24** | Keywords (`type`, `check`, `plan`, `result`, `empty`, `optional`, …) can't be record field names in v0.1, so JSON with a key like `{"type": …}` can't be decoded into a record field of that name. Preferred answer: make keywords contextual after `.` and in field declarations, so a field position accepts them as plain names; additive, so it needs an RFC (`delivery/52` §9). | Open · default: keywords stay reserved everywhere (current spec); target v0.1 or v0.2 |

## 5. Prior art

Reviewed 2026-09-25/26 to position Velme and harvest lessons. No single system combines build-time LLM synthesis into a
small IR, a validator as trust boundary (INV-1), deterministic checks (INV-2) and a lock; each piece has precedent.

| Family | Examples | Shared with Velme | Difference | Lesson |
|---|---|---|---|---|
| Program synthesis | Sketch, Rosette, SyGuS, Synquid | small target language, spec with holes, external checker | solver/enumerative search, tiny programs; Velme proposes with an LLM and verifies by testing | counterexample-guided retry is R-SYNTH-11 |
| Programming by example | FlashFill / PROSE | examples drive synthesis (D-7) | fixed per-domain DSLs with ranking | examples underspecify: Q-12 |
| Verified languages | Dafny, F\*, Liquid Haskell, Verus, Eiffel | pre/postconditions (`check` ≈ `ensures`) | they prove for all inputs; Velme tests a bounded set (§7 of `compiler/22`) | preconditions: Q-10 |
| Property-based testing | QuickCheck, Hypothesis, proptest | Velme's verification is PBT | they test human code | shrinking Q-8, failure database Q-9 |
| LLM frameworks | DSPy, BAML, Marvin, Instructor, Outlines, LMQL | declarative typed goals sent to a model | they call the model on every run; Velme once per build, then runs locked code | schema-constrained output, already R-SYNTH-09 and the `ollama` `format` field (D-41) |
| AI coding assistants | Copilot, Cursor, Claude Code, Kiro, Spec Kit | describe intent, get code | emit general source a human must own; no trust boundary or lock | best-of-n sampling (CodeT, AlphaCodium): Q-11 |
| Reproducible builds | Nix, Bazel, Cargo.lock, Unison | content-addressed keys and lock (R-ART-03) | they lock human inputs; Velme also locks model output | remote cache: Q-13 |
| Capabilities | Deno permissions, WASI components | no ambient authority (INV-4) | — | effect grants: Q-14 |

Two cautions: a spec that is as hard to write as the code sank adoption of Sketch and Dafny, so `plan` plus checks must
stay much shorter than the code it replaces; and English-like syntax invites ambiguity (AppleScript, Inform 7), so the
grammar stays strict (`language/10`).
