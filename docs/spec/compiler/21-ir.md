# 21 — Velme IR

**Status:** v0.1 · **Area:** IR
**Read when:** changing an IR node, the JSON schema, the IR validator, lowering from HIR, or anything that reads or writes IR artifacts.
**Depends on:** [SPEC](../SPEC.md), [20-compiler-architecture](20-compiler-architecture.md), [language/11](../language/11-types.md), [language/14](../language/14-builtins.md)
**Source:** §3.1, §15, §16, §17, §22

## 1. Purpose & boundaries

Velme IR is the typed, JSON-serializable program representation that sits between the front end and every back end.
Spellbook returns IR (never WASM, INV-1); the validator in this file is the trust boundary; the interpreter
([runtime/30](../runtime/30-execution-vibevm.md)) defines its meaning; the WASM backend
([runtime/31](../runtime/31-wasm-sandbox.md)) compiles it. Type rules are those of [language/11](../language/11-types.md);
built-in names and signatures come from [language/14](../language/14-builtins.md).

IR is a compiler/runtime concept — learners never write it (§16). They can view it with `velme build --emit ir`.

## 2. Goal envelope

```json
{
  "ir_version": "0.1",
  "builtins_version": "0.1",
  "goal": "BuildPlayerSummary",
  "types": {
    "Player":  { "fields": [["name", {"t": "Text"}], ["jump_height", {"t": "Number"}], ["score", {"t": "Number"}]] },
    "Summary": { "fields": [["score", {"t": "Number"}], ["rank", {"t": "Number"}], ["badge", {"t": "Text"}]] }
  },
  "inputs": [["player", {"t": "Record", "name": "Player"}]],
  "output": {"t": "Record", "name": "Summary"},
  "calls": [ /* Call nodes, compiler-produced only (§4) */ ],
  "body": { /* one expression node */ }
}
```

**R-IR-01** An IR goal is self-contained: `types` lists exactly the record types reachable, through fields too, from
`inputs`, `output` and the signatures of the goals in `calls`, with fields in declaration order; `body` names no other
(D-84). The validator checks it against the HIR types (§6 stages 3–4).
**R-IR-02** `calls` is present only for composite goals and is produced by the compiler from the `call` block. A
synthesized candidate must omit `calls` (or send `[]`); any `Call` node from Spellbook is rejected with `VL0402` (D-5).
**R-IR-03** `body` is the leaf implementation, the composite tail, or — for a wired goal (D-4) — `{"kind":"local","name":"result"}`.

### 2.1 Types

| Type | JSON |
|---|---|
| `Number` / `Text` / `Boolean` / `Nothing` | `{"t":"Number"}` / `{"t":"Text"}` / `{"t":"Boolean"}` / `{"t":"Nothing"}` |
| `T?` | `{"t":"Optional","of":T}` |
| `List<T>` | `{"t":"List","of":T}` |
| record | `{"t":"Record","name":"Player"}` |

`T` is assignable to `T?`; there is no explicit wrap node. `Optional(Optional(T))` is normalized to `Optional(T)`.

## 3. Expression nodes

Every expression is an object with a `kind`. Names below are exhaustive for `ir_version` 0.1.

| Node (§16) | `kind` | JSON shape | Type rule (summary) |
|---|---|---|---|
| Literal | `literal` | `{"kind":"literal","type":T,"value":<json>}` | `value` must decode as `T` under the D-23 mapping; numbers finite |
| Input | `input` | `{"kind":"input","name":"player"}` | type of that input |
| Local | `local` | `{"kind":"local","name":"score"}` | call binding, `let` name or lambda parameter in scope |
| Record | `record` | `{"kind":"record","type":"Summary","fields":{"score":E,…}}` | exactly the declared fields, each assignable |
| List | `list` | `{"kind":"list","of":T,"items":[E,…]}` | each item assignable to `T` |
| FieldGet | `field` | `{"kind":"field","of":E,"field":"score"}` | `E` is a record (not optional) with that field |
| BinaryOp | `binary` | `{"kind":"binary","op":OP,"left":E,"right":E}` | `add sub mul div` Number×Number→Number; `lt le gt ge` Number→Boolean; `eq ne` same type, or one side assignable to the other (R-TYP-20) →Boolean (structural; a present value against `nothing` is `false` for `eq`, `true` for `ne`, D-61); `and or` Boolean, short-circuit |
| UnaryOp | `unary` | `{"kind":"unary","op":"neg"\|"not"\|"is_empty","arg":E}` | `neg` Number; `not` Boolean; `is_empty` on `T?`, `List`, `Text` → Boolean; on `List<T>?`/`Text?` also `true` for a present-but-empty value (D-60) |
| Let / Sequence | `let` | `{"kind":"let","bind":[["x",E],…],"body":E}` | sequential; each name visible to later binds and `body`; no shadowing |
| Condition | `if` | `{"kind":"if","cond":E,"then":E,"else":E}` | `cond` Boolean; branches unify (`T` and `Nothing` unify to `T?`) |
| Narrow | `unwrap_or` | `{"kind":"unwrap_or","of":E,"default":E}` | `E: T?`, `default: T` → `T` |
| Map | `map` | `{"kind":"map","list":E,"fn":{"param":"p","body":E}}` | `List<A>` → `List<B>` |
| Filter | `filter` | `{"kind":"filter","list":E,"fn":{"param":"p","body":E}}` | body Boolean; → `List<A>` |
| Find | `find` | `{"kind":"find","list":E,"fn":{"param":"p","body":E}}` | first match → `A?` |
| Reduce | `reduce` | `{"kind":"reduce","list":E,"init":E,"fn":{"acc":"a","param":"p","body":E}}` | `init: B`, body `B` → `B` |
| Sort | `sort_by` | `{"kind":"sort_by","list":E,"key":{"param":"p","body":E},"descending":Boolean}` | key Number only (D-59); **stable** |
| All | `all` | `{"kind":"all","list":E,"fn":{"param":"p","body":E}}` | body Boolean; short-circuits at the first `false`; `true` for `[]` (D-58) |
| Any | `any` | `{"kind":"any","list":E,"fn":{"param":"p","body":E}}` | body Boolean; short-circuits at the first `true`; `false` for `[]` (D-58) |
| Builtin call | `builtin` | `{"kind":"builtin","name":"maximum","args":[E,…]}` | signature from the catalog of `builtins_version` (language/14) |
| Call | `call` | only inside `calls` (§4) | compiler-only (D-5) |

**R-IR-04** Lambdas exist only as the `fn`/`key` of a collection node (`map`, `filter`, `find`, `reduce`, `sort_by`,
`all`, `any`). They are not values: no node can store, return or pass a lambda. Lambda bodies may reference enclosing
locals, inputs and their own parameters. Elements are visited in list order for every collection node, matching
[language/14](../language/14-builtins.md) R-BLT-07.
**R-IR-05** Narrowing in IR is explicit: a `field` on an optional is invalid; the producer uses `if` + `is_empty`
followed by `unwrap_or`, or `find`/`unwrap_or`. (The check DSL's implicit narrowing, language/13, is lowered to this.)
**R-IR-06** `Condition` is an **expression** conditional (needed by leaf goals such as `FindBadge`, §44). Conditional
*calls* (§13) remain Future; `if` cannot guard a `Call`.
**R-IR-07** `sort_by` is stable: elements with equal keys keep their input-list relative order, in both directions of
`descending`. Keys are `Number` only in v0.1 (D-59); `Text` ordering is deliberately deferred until collation is
decided (R-TYP-09, R-BLT-03) — a `Text`-typed key is rejected by the validator (§6) with `VL0402`.
**R-IR-08** Division by zero, overflow, and a non-integer where an integer is required fail at run time with
`VL0602` (D-36). The validator does not try to prove their absence.

## 4. Call nodes (compiler-only)

```json
{ "kind": "call", "binding": "score", "goal": "CalculateScore",
  "goal_signature": "b3:5f1c…", "args": [ {"kind": "input", "name": "player"} ] }
```

**R-IR-09** `calls` lists bindings in source order. `args` are positional, may reference inputs and **earlier**
bindings only (§12.5), and contain no `call`. `goal_signature` is the child's signature fingerprint (runtime/32 §2).
**R-IR-10** The runtime derives waves from `args` references, never from list position (§9: source order ≠ execution order).

## 5. Corrected §15 example (F-1)

`BuildPlayerSummary` is composite. The compiler produces `calls`; Spellbook produces only `body`.

```json
{
  "ir_version": "0.1", "builtins_version": "0.1", "goal": "BuildPlayerSummary",
  "types": { "Player": {…}, "Summary": {…} },
  "inputs": [["player", {"t": "Record", "name": "Player"}]],
  "output": {"t": "Record", "name": "Summary"},
  "calls": [
    {"kind": "call", "binding": "score", "goal": "CalculateScore", "goal_signature": "b3:…", "args": [{"kind": "input", "name": "player"}]},
    {"kind": "call", "binding": "rank",  "goal": "CalculateRank",  "goal_signature": "b3:…", "args": [{"kind": "input", "name": "player"}]},
    {"kind": "call", "binding": "badge", "goal": "FindBadge",      "goal_signature": "b3:…", "args": [{"kind": "input", "name": "player"}]}
  ],
  "body": {
    "kind": "record", "type": "Summary",
    "fields": {
      "score": {"kind": "local", "name": "score"},
      "rank":  {"kind": "local", "name": "rank"},
      "badge": {"kind": "local", "name": "badge"}
    }
  }
}
```

Leaf example — `FindHighestJumpingPlayer(players: List<Player>) -> Player?`:

```json
{ "kind": "let",
  "bind": [["best", {"kind": "builtin", "name": "maximum",
                     "args": [{"kind": "map", "list": {"kind": "input", "name": "players"},
                               "fn": {"param": "p", "body": {"kind": "field", "of": {"kind": "local", "name": "p"}, "field": "jump_height"}}}]}]],
  "body": {"kind": "find", "list": {"kind": "input", "name": "players"},
           "fn": {"param": "p", "body": {"kind": "binary", "op": "eq",
                  "left": {"kind": "field", "of": {"kind": "local", "name": "p"}, "field": "jump_height"},
                  "right": {"kind": "unwrap_or", "of": {"kind": "local", "name": "best"}, "default": {"kind": "literal", "type": {"t": "Number"}, "value": 0}}}}} }
```

## 6. Validation (§22 steps 1–7)

Stages run in order; the first failing stage stops validation and returns all its diagnostics (fed back to the LLM on
retry, 22 §5). Steps 8–9 (execute, checks) are verification, owned by [22](22-spellbook-synthesis.md) §6.

| Stage | Rule | Failure |
|---|---|---|
| 1 Schema | **R-IR-11** JSON parses and validates against the generated JSON Schema of `ir_version`. | `VL0401` |
| 2 Structure | **R-IR-12** Limits (§7) hold; `kind`s known; lambda param names unique in scope; no shadowing; `calls` absent in synthesized output (R-IR-02); the candidate's `ir_version` and `builtins_version` equal the request's own (D-63). | `VL0402` |
| 3 Names | **R-IR-13** Every `input`/`local`/`field`/record type/builtin name resolves against the catalog of `builtins_version`; `goal` equals the requested goal; `types` holds no record type that R-IR-01 doesn't reach (D-84). An unresolved or unknown-builtin name is rejected here, not at stage 5 (D-63). | `VL0402` |
| 4 Types | **R-IR-14** Bottom-up type check per §3; `types` equal HIR record types; `inputs`/`output` equal the HIR signature; `body` assignable to `output`. | `VL0402` |
| 5 Capabilities | **R-IR-15** No host function, capability or unknown field appears (INV-4). v0.1 IR has no node that can name a host function, so this stage guards against schema extensions; builtin names are resolved at stage 3 (D-63). | `VL0801` |
| 6 Call graph | **R-IR-16** `calls` equals the compiler's binding list exactly (names, goals, signatures, args); synthesized IR contains no `call` (INV-6). | `VL0402` |
| 7 Resources | **R-IR-17** Static bounds: node count, nesting depth, collection-op nesting ≤ 4 (lambdas only, D-79), literal sizes; all dynamic cost is metered by fuel at run time (runtime/30 §7). | `VL0402` |

**R-IR-18** The validator is deterministic, total (never panics on any JSON input — fuzz target, `delivery/51`) and has
no knowledge of which provider produced the IR.
**R-IR-19** Diagnostics from validation name the JSON path (`/body/fields/rank/name`) and, where possible, the
source span of the goal, so both the LLM (retry) and the learner (`--verbose`) can act on them.

## 7. Limits

| Limit | v0.1 value |
|---|---|
| Nodes per goal | 10 000 |
| Expression nesting depth | 128 |
| Collection-op nesting: a collection op inside another's lambda (`map` whose `fn` filters …); one in `list` position doesn't count (D-79) | 4 |
| Items in a `list` literal | 1 000 |
| `Text` literal length | 64 KiB |
| Serialized IR size, as received and in canonical form (R-IR-21; what a store keeps) | 1 MiB |

Limits are constants in `velme-ir`, referenced by name from the validator, the prompt builder and tests.

## 8. Schema, canonical form, versioning

**R-IR-20** Rust types in `velme-ir` are the single source of truth; the JSON Schema is generated with `schemars` and
committed (`crates/velme-ir/schema/ir-0.1.json`). A test fails if the committed schema differs from the generated one.
The same schema file is what the prompt embeds and what structured output is constrained to (22 §4).
**R-IR-21** Canonical JSON (D-21) is JCS-like, not JCS (RFC 8785): it differs in key order and number form.

- object keys sorted by Unicode code point, which equals UTF-8 byte order — not by UTF-16 code units as JCS sorts, which
  differs for keys beyond the BMP;
- strings escape only `"`, `\` and U+0000–U+001F: the short forms `\b \f \n \r \t` where they apply, else lowercase
  `\u00xx`; every other code point is raw UTF-8 with no normalization (NFC etc.) — bytes are hashed as given;
- numbers in the plain decimal rendering of R-TYP-08 (decoded exactly, never via binary float), `-0` written as `0`
  — never JCS's ES6 exponent forms such as `1e+21`;
- no insignificant whitespace;
- a duplicate object key is rejected on input: `VL0401` for an IR document (schema stage, §6), `VL0902` for input JSON
  ([language/11](../language/11-types.md) §10, [tooling/40](../tooling/40-cli.md) owns `velme run` input decoding).

Hashes and artifacts always use canonical form; `--emit ir` pretty-prints. Golden vectors (canonical JSON string →
BLAKE3 hex, computed with the `blake3` crate over the UTF-8 bytes shown). The last three are the canonical form of
`{"😀":2,"｡":1}`, `{"n":1e21}` and `{"n":1e-7}`, where JCS would keep `😀` (UTF-16 `D83D DE00`) before `｡` (`FF61`)
and write `1e+21` and `1e-7`:

| Canonical JSON | BLAKE3 |
|---|---|
| `{"a":3,"b":1,"é":2}` | `7d56b0352359754359630cf7b7b84db97df2d79f02a5ae541912a1dee18688d6` |
| `{"s":"line1\nline2\ttab\"quoteé"}` | `0856a95de184ff551d749d960cbe5f544945772b29a30393420f339d80449862` |
| `{"n":0.1}` | `5b7a23a0b8b66250921682288e8176595b285f99ee4cf48fdb74d94ce1d23f3d` |
| `{"｡":1,"😀":2}` | `899b786e1c7b7f49e7315b2211771e725f2fd047cf784a9400d66bca18e9f843` |
| `{"n":1000000000000000000000}` | `9fc33899cf05af9c90c9aceb75c5b16c651ecb9e0cc703147a574ea8d530e185` |
| `{"n":0.0000001}` | `a06f5c50a25acd77e208ba662c6054caba0776076d697837e4cb0984fe154db9` |
**R-IR-22** `ir_version` is `MAJOR.MINOR`; its compatibility unit is MAJOR, or MAJOR.MINOR while MAJOR is 0 (D-85).
From 1.0 a minor bump is additive (new optional field or node kind); a validator accepts any IR of its own
compatibility unit whose minor ≤ its own, so before 1.0 only its own version. A new compatibility unit changes
`contract_key` (runtime/32 R-ART-23), so old artifacts are re-synthesized, never reinterpreted.
**R-IR-23** Every node kind has at least one golden IR file and one interpreter test before it is released.

## 9. Acceptance criteria

| ID | Criterion |
|---|---|
| AC-IR-01 | The committed JSON Schema equals the one generated from the Rust types. |
| AC-IR-02 | Synthesized IR containing a `call` node, or a non-empty `calls`, is rejected with `VL0402` (INV-6). |
| AC-IR-03 | IR whose `body` type differs from the declared output (e.g. `Text` for `Number`) is rejected with `VL0402` naming the JSON path. |
| AC-IR-04 | IR using a builtin not in the catalog is rejected with `VL0402` (D-63), naming the unresolved name. |
| AC-IR-05 | IR exceeding each §7 limit is rejected with `VL0402`; IR exactly at the limit is accepted. |
| AC-IR-06 | The validator never panics on the fuzz corpus (arbitrary JSON and schema-valid mutations). |
| AC-IR-07 | Canonical serialization is byte-identical across Linux/macOS/Windows for the golden IR set. |
| AC-IR-08 | The corrected §15 example validates and, run on the interpreter with stub children, returns `{score, rank, badge}`. |
| AC-IR-09 | An IR file with the same major and a higher minor than the validator is rejected with a message naming both versions. |
| AC-IR-10 | `all([], f)` validates with type `Boolean`; `all`/`any` whose lambda body is not `Boolean` are rejected with `VL0402` (D-58). |
| AC-IR-11 | A `sort_by` whose `key` lambda returns `Text` is rejected with `VL0402`; one returning `Number` validates (D-59). |
| AC-IR-12 | `is_empty` accepts a `List<T>?`/`Text?` operand and validates with type `Boolean` (D-60). |
| AC-IR-13 | An `eq`/`ne` node comparing a `Number` and a `Number?` operand validates (R-TYP-20); comparing two operands with no assignability either way is rejected with `VL0402` (D-61). |
| AC-IR-14 | A candidate whose `ir_version` or `builtins_version` differs from the request's own is rejected with `VL0402` naming both versions (D-63). |
